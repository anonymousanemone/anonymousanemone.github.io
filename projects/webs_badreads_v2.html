Overview

An index card system for fic

Archive-of-Our-Own-style fanfiction doesn't fit neatly into a bookshelf: one work can belong to several fandoms, ship several character pairings, and carry a couple dozen free-text tags. BadReads models that as a proper relational schema — nine linked tables at launch, extended in a second pass with array columns, a full-text search vector, and a data-integrity trigger — then exposes it through a search-first Flask app with no client-side framework, just Jinja templates and parameterized SQL.

Features

What the app actually does

search

Multi-filter query builder

Title, author, fandom, tags, word-count range, update-date range, and completion status combine into one dynamically built SQL query with bound parameters.

detail page

Generated fic pages

No hardcoded pages — one template pulls fandoms, ships, characters, tags, ratings, and comments for any fanfic_id via a shared join.

discovery

Recommendation engine

Suggests five other works sharing the same author, fandom, tag, or ship pairing — computed live with a correlated subquery, not cached.

community

Ratings & comments

One rating per user per fic (1–10), unlimited comments. New usernames are created on first interaction rather than requiring signup.

profiles

Author pages

Every username is a live page listing everything that author has written, generated the same way as the fic detail view.

v2

Full-text summary search

A tsvector column over title + summary lets queries match on plot content, not just structured metadata.

Stack

Two drawers: product and data

Product layer

  • Python 3 / Flask — routing, request handling
  • Jinja2 — server-rendered templates
  • SQLAlchemy Core — connection + parameterized text() queries, no ORM
  • Vanilla HTML/CSS — no client framework, no build step
  • GCP Compute VM — hosted the live instance (now decommissioned)

Data layer

  • PostgreSQL — 9 base tables, 3NF-normalized
  • Dynamic SQL — filters appended conditionally, bound params throughout
  • tsvector — full-text search over title + summary
  • Array columns — free-form tags, replacing a fixed Tag table
  • PL/pgSQL trigger — rejects case-insensitive duplicate tags on write

Schema

Under the hood

The schema separates works from the fandom taxonomy that describes them: a Fanfic is linked to characters and ships through Has_Char / Has_Ship, which in turn reference a shared Character_Part_Of / In_Relationship vocabulary — so the same character or ship pairing can be reused across many works without duplication.

Data-integrity trigger — no duplicate tags, case-insensitive

CREATE TRIGGER DistinctTagsOnFanfic
BEFORE INSERT OR UPDATE ON Fanfic
FOR EACH ROW EXECUTE FUNCTION check_distinct_tags();

-- rejects the insert below: 'AU' appears twice
INSERT INTO Fanfic (fanfic_id, tags)
VALUES (1, ARRAY['AU', 'Enemies to Lovers', 'AU']);

Full-text search over title + summary

SELECT fanfic_id, title, summary
FROM Fanfic
WHERE to_tsvector('english', title || ' ' || summary)
